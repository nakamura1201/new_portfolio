# 体系的デバッグ & 調査スキル

このスキルは、ライブラリや言語に依存せず、問題の根本原因を最短で特定し、品質の高い解決策を選択するための標準プロセスを定義します。

## 1. 調査の標準プロセス (4ステップ)

### ステップ 1: 事象の定義 (Define)

単に「動かない」ではなく、以下の 2 点を明確にします。

- **期待値 (Expected)**: 本来どう動くべきか。
- **現状 (Actual)**: 実際には何が起きているか。
- **確認手段**: Console ログ、Network レスポンス、Computed スタイル。

### ステップ 2: 切り分け (Isolate)

影響範囲を限定し、原因の所在を突き止めます。

- **境界の特定**: Frontend vs Backend? CSS vs JS?
- **依存の排除**: 外部ライブラリ（GSAP 等）を無効化しても発生するか？
- **再現環境**: 特定のブラウザ、特定の画面幅、キャッシュの有無。

### ステップ 3: 最小再現 (Minimize)

問題の核心部分だけを抽出したコードを作成します（エージェントへの指示や外部質問にも有効）。

- 不要な HTML 要素や CSS クラスを削除しても再現するか？
- 最小限の JS ロジックだけで再現するか？

### ステップ 4: 解決策の評価 (Evaluate)

複数の解決案がある場合、以下の基準で「最適」を選びます。

1. **堅牢性**: ブラウザ更新や将来のコード変更に耐えられるか。
2. **パフォーマンス**: 描画 FPS やレスポンス速度を損なわないか。
3. **保守性**: コードが読みやすく、ハック的な手法（マジックナンバー等）でないか。

## 2. ツール活用ガイド

### ブラウザ・デベロッパーツール

- **Elements**: `Computed` タブでスタイルの最終継承値を確認。`Break on...` で DOM の変更を監視。
- **Network**: API のステータスコード、レスポンスヘッダ（CORS 等）、ペイロードを確認。
- **Performance**: GSAP 等の重い処理がメインスレッドを占有していないか、FPS の低下を調査。

### ロギング・デバッグ手法

- **ロジック追跡**: `console.table()` でオブジェクトを可視化、`console.trace()` でコールスタックを確認。
- **API 調査**: `curl` や `Postman` を用いて、フロントエンドの不備かバックエンド由来かを切り分け。

## 3. 実装チェックリスト

- [ ] 現象を数値や具体的な動作で表現したか（例：「遅い」→「LCP 2.5s超」）
- [ ] 原因が特定できるまで安易に「修正」コードを書いていないか
- [ ] 解決策が「対症療法」ではなく「根本原因」へのアプローチになっているか
- [ ] 修正後に副作用（他の部分のレイアウト崩れ等）がないかテストしたか
